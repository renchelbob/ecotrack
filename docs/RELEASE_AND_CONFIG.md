# Регламент работы с конфигурациями, секретами и релизами EcoTrack

Документ определяет правила управления переменными окружения, хранения секретов, версионирования и поставки сборок проекта EcoTrack с учётом требований 152-ФЗ РФ.

---

## 1. Контуры и окружения

| Контур | Ветка / триггер | Назначение | Инфраструктура |
| :--- | :--- | :--- | :--- |
| `local` | Локальная `feature/*` | Разработка и отладка | Локальный Docker (`docker-compose.yml`), `.env` из `.env.example` |
| `staging` | `push` в `develop` | Предрелизная проверка и демонстрация MVP | GitHub Environment `staging`, образ `ghcr.io/renchelbob/ecotrack-api:staging`, deploy-bundle артефакт |
| `production` | Тег `vX.Y.Z` на `main` | Целевой релизный контур | GitHub Environment `production`, образ `ghcr.io/renchelbob/ecotrack-api:vX.Y.Z`, GitHub Release; при выводе в эксплуатацию — хостинг в РФ (152-ФЗ) |

---

## 2. Конфигурации и управление секретами

### 2.1 Шаблон `.env.example` и локальный `.env`
1. Единственный конфигурационный файл, хранимый в Git — [`.env.example`](../.env.example). В нём перечислены все обязательные переменные приложения с учебными/шаблонными заглушками и без реальных паролей или ключей доступа.
2. Локальный `.env`, приватные ключи (`*.pem`, `*.key`) и каталог `secrets/` занесены в [`.gitignore`](../.gitignore). Перед локальным запуском разработчик копирует шаблон:
   ```bash
   cp .env.example .env
   ```
   и при необходимости генерирует локальные ключи JWT/HMAC (`openssl rand -hex 32`).
3. Добавление новой переменной окружения в код обязательно сопровождается обновлением `.env.example` в том же PR. Отсутствие обязательных переменных из базового набора проверяется в CI (`Contracts & Config Gate`).

### 2.2 Секреты в CI/CD и запрет утечек
1. Секреты тестового и релизного контуров задаются исключительно через **GitHub Repository / Environment Secrets** (`staging`, `production`) или `.env` непосредственно на целевом сервере/демо-ПК.
2. В репозитории запрещено:
   - коммитить токены доступа (`ghp_`, `github_pat_`, ключи API), пароли БД, JSON сервисных аккаунтов FCM;
   - прописывать PAT-токены в URL удалённого репозитория (`.git/config`) — локальная аутентификация выполняется через credential helper (`git credential`);
   - выводить персональные данные пользователей, токены и секреты в логи приложения и CI (`specs/03-backend-architecture-and-152fz.md`).
3. При каждом push и PR в CI выполняется автоматический поиск сигнатур открытых токенов в отслеживаемых файлах.

## 3. Версионирование и `CHANGELOG.md`

Проект использует схему **SemVer 2.0.0** (`vMAJOR.MINOR.PATCH`):
- `MAJOR` (`v1.0.0`) — выпуск готового MVP к финальной защите или несовместимое изменение контракта API/БД;
- `MINOR` (`v0.1.0`, `v0.2.0`) — плановый релиз по итогам спринта с новой обратно-совместимой функциональностью;
- `PATCH` (`v0.1.1`) — релизное исправление (`hotfix/*`) без расширения функциональности.

Все пользовательские, контрактные и инфраструктурные изменения фиксируются в [`CHANGELOG.md`](../CHANGELOG.md) в секции `[Unreleased]` по мере слияния PR в `develop`, а при создании ветки `release/vX.Y.Z` переносятся под заголовок `[X.Y.Z] — ГГГГ-ММ-ДД`.

## 4. Автоматизированный CD-пайплайн и поставка релизов

Конфигурация поставки описана в [`.github/workflows/cd.yml`](../.github/workflows/cd.yml):

1. **Поставка в `staging` (`develop`)**:
   - Собирает облегчённый runtime-образ `backend/Dockerfile` (`--target runtime`, Python 3.14, непривилегированный пользователь `ecotrack`, бюджет размера окружения `<= 100 МБ`).
   - Публикует образ в GitHub Container Registry: `ghcr.io/renchelbob/ecotrack-api:staging` и `:sha-<commit>`.
   - Поднимает эфемерный контейнер `postgis/postgis:17-3.5-alpine`, загружает `contracts/schema.sql` и проверяет старт runtime-образа.
   - Формирует и сохраняет в артефактах `ecotrack-staging-deploy-bundle` (`docker-compose.deploy.yml`, `contracts/schema.sql`, `contracts/openapi.yaml`, `contracts/error_catalog.json`, `.env.example`).

2. **Релизная поставка `production` (тег `vX.Y.Z`)**:
   - Публикует неизменяемый образ `ghcr.io/renchelbob/ecotrack-api:vX.Y.Z` и тег `:latest`.
   - Упаковывает `ecotrack-vX.Y.Z-deploy-bundle.tar.gz` с зафиксированной версией образа.
   - Автоматически создаёт запись в **GitHub Releases** сгенерированными примечаниями к выпуску и приложенными артефактами (deploy-архив и актуальный `contracts/openapi.yaml`).

## 5. Развёртывание на локальном стенде демонстрации и откат

### 5.1 Запуск релизной сборки на демо-ПК (или VPS в РФ)
1. Скачать архив `ecotrack-vX.Y.Z-deploy-bundle.tar.gz` со страницы нужного GitHub Release (или `ecotrack-staging-deploy-bundle` из последнего прогона CD).
2. Распаковать, создать `.env` из `.env.example` и задать актуальные пароли/секреты (локально порты БД и API привязаны к `127.0.0.1`).
3. Поднять стек готовыми образами без локальной пересборки:
   ```bash
   docker compose -f docker-compose.deploy.yml pull
   docker compose -f docker-compose.deploy.yml up -d
   ```

### 5.2 Процедура отката (Rollback)
1. **Откат приложения**: указать предыдущий стабильный тег образа в `docker-compose.deploy.yml` (например, `v0.1.0` вместо `v0.2.0`) и выполнить:
   ```bash
   docker compose -f docker-compose.deploy.yml up -d api
   ```
2. **Откат схемы БД**: перед накатом миграций на целевом сервере снимается бинарный дамп (`pg_dump -Fc`); при несовместимом изменении схемы выполняется восстановление через `pg_restore --clean --if-exists`.
3. После отката создаётся ветка `hotfix/EC-XX-*` от `main` для разбора причины и выпуска исправленного патч-релиза.
